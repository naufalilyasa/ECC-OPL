## Summary

Design a zero-dependency **reference harness**, fixture-only evidence contract, and non-production gate for M4. The harness exercises D02, C01, C04, C05, C06, C08, C10 and negative mutations 10/12 without starting a browser, spawning a runner, sending a request, writing a real registry, or installing anything. Successful fixture assertions are not proof of live `/e2e`, Playwright, safety-gate enforcement, or actual user coverage; those remain `DEFERRED_TO_M6`.

## Affected User and Ideal State

**Affected users:** An engineer uses `/e2e run` or `full` to obtain truthful, reviewable journey coverage. The `/e2e` orchestrator and `e2e-runner` consume the environment authorization and evidence contracts, while an owner controls which non-production operations may run. Today M3 supplies reference-only registry governance, and the command provides only part of the runner contract; neither constitutes a live hardened runner.

| Row | Statement | Reason |
|---|---|---|
| IS-1 | A production, unknown, denied, or insufficiently authorized target is blocked before dispatch/spawn/network; a precise permitted non-production environment and operation can pass the gate. | The owner never authorizes unsafe or unintended side effects. (AC-011) |
| GAP-1 | M3's `fullPhaseTrace` models only an authorization boolean and `e2e.md` §3.2 asks for an authorized environment without the complete per-operation evidence. | That reference does not establish the DEC-07 boundary. |
| IS-2 | Exit zero with weak or only visibility assertions is `PASS_UNVERIFIED`, never `covered`. | An apparently green test cannot misrepresent behavioral coverage. (AC-012) |
| GAP-2 | `e2e.md` states the desired mapping, but M3 provides no runnable runner-result quality evaluator. | There is no M4 fixture-level proof that weak tests cannot earn credit. |
| IS-3 | A nonzero exit is `FAIL`; a formerly covered row receives an `unverified` proposal rather than a false pass or an automatic write. | Failures remain visible and previously asserted coverage is not silently retained. (AC-013) |
| GAP-3 | M3's registry reference only models verified-pass splicing and does not validate a failed runner outcome. | Failure handling and the no-write downgrade proposal are unproven. |
| IS-4 | Coverage can be proposed only from a persistent Playwright spec and a complete, identity-matched, scoped, redacted, observed runner record; missing facts stay missing. | The engineer can trace coverage to real test behavior without fabricated CLI, hashes, or artifacts. (AC-014; DEC-08) |
| GAP-4 | `e2e.md` §3.3 requests only `Spec`, `Node`, `Command`, `Exit`; `agents/e2e-runner.md` prefers Agent Browser and includes an installation example, conflicting with DEC-09. | Current instructions neither encode the full evidence contract nor consistently enforce the approved baseline. |

- Implement **only a reference/harness-level model** under `docs/e2e-v2/m4/**`, using synthetic F10/F12 inputs, zero-dependency Node.js and isolated temporary fixtures. Distinguish synthetic observations from actual runner evidence everywhere.

- Produce machine-readable reference reports, RED/GREEN TDD evidence, and an explicit two-layer traceability handoff. Report coverage ≥80% **lines, branches and functions** for each new non-test module, separately from any project-wide coverage.
- Hash-check frozen M1/M2/M3 artifacts and specified upstream sources before/after. - No writes outside `docs/e2e-v2/m4/**`, except the **optional, separately owner-approved exact command delta** in Phase 4. Temporary fixture files must be under the approved OpenCode scratch directory. The plan file itself is the planning-only exception.
- No changes to M1/M2/M3, contracts, decisions, `agents/e2e-runner.md`, `.opencode/prompts/agents/e2e-runner.txt`, package files, or `.gitignore`. `TESTS.md` and `.governance/docs-map.json` stay absent.

## Reference Contract to Implement

1. **Pre-dispatch gate.** For both `run` and `full`, require a parseable exact base URL, non-production classification, named service, account class, fixture ownership, network scope, and requested mutation/operation list. Require explicit authorization bound to the exact environment/target **and each requested operation**; high-risk money/stock/approval/notification/cross-tenant operations have no blanket approval. Production or unknown classification, malformed/missing fields, target or operation mismatch, no authorization, or Guardian denial yields `BLOCKED` before a dispatch callback is touched. Missing already-installed Playwright, when it is relevant to a future real run, yields `BLOCKED_DEPENDENCY`; this M4 harness never checks by invoking it. For C08, inject a synthetic dependency-availability input: only an explicit available value with an otherwise valid fixture may reach the spy; missing/unavailable yields `BLOCKED_DEPENDENCY`, zero spy calls, and no installation or Playwright probe. All approvals used in tests are synthetic.
2. **Runner evidence.** Validate conceptual R1 fields `test_id`, `flow`, `spec`, `spec_sha256`, `test_node`, `command`, `exit_code`, `runner_status`, `assertion_summary`, `target_environment`, `artifacts`, `start_time`, `end_time`, `redaction_status`, plus test counts and retry/flakiness information. Require exact test ID/node/environment, repo-relative persisted spec, realpath containment and recomputed SHA-256; validate actual CLI is separately observed and matches the allowed invocation, not `/e2e` or untrusted `Command:` data. Exit and counts must be finite non-negative integers, start/end ordered, counts and status consistent; zero, skipped, `fixme`, or all-filtered cannot receive credit. Compare current synthetic test and assertion counts independently against synthetic prior-stage counts: either decrease produces an explicit count-regression anomaly, no `COMPLETE`, no fixture `PASS_VERIFIED` and no credit; unchanged counts may pass the count gate. Preserve a trustworthy nonzero exit as `FAIL` even when an anomaly is also reported.
3. **Synthetic observations.** Define an explicit fixture provenance marker and a separate mock observer record for CLI, execution result, identity, counts, and artifacts; compare the returned envelope against that record instead of allowing the envelope to attest to itself. For C01, build a synthetic handoff from a registered fixture row and independently bind its exact ID, spec path and observable expectation plus its allowed invocation to an immutable pre-tamper row/allowlist snapshot. A changed handoff expectation or spec must not yield fixture `PASS_VERIFIED` or any credit, even if echoed by the observer; handoff construction dispatches no runner. This demonstrates only validator behavior over fixtures. Never call the mocked CLI string or equate a matching simulated record to real-world observation. Report real/live fields as `NOT_RUN` or `DEFERRED_TO_M6`.
4. **Assertion quality.** Model an explicit meaningful expected-behavior/state transition and observed result in trusted test fixtures; visibility-only, tautological, zero or unknown assertions are weak, including mutation 10. Do not pretend generic string matching proves real behavioral quality. Real assertion provenance/quality remains an M6 validation problem.
5. **Artifact safety.** Fixture project and ignored artifact root live under a freshly created scratch directory; create a fixture `.gitignore` there, never touch repo `.gitignore` or `.git`. For the known fixture root `artifacts/`, require a matching literal `artifacts/` rule in that fixture file; a missing or unrelated rule rejects before fixture credit. This check covers only the defined fixture rule and does not inspect `.git` or claim real Git ignore verification. Check existing regular files, repo/scoped-root containment, `..`, absolute paths as appropriate, symlink escapes at any component, and missing files. Use explicit safe, synthetic text samples for token/cookie/password/PII/private-URL redaction tests; redact or reject before publishing. Unknown/binary/uninspectable artifacts cannot be presumed safe, and `redaction_status: passed` alone is not sufficient. A generic string scrubber must not be presented as a proof for real traces/screenshots.
6. **Outcome precedence.** A trustworthy nonzero exit yields `FAIL` even if evidence is otherwise incomplete; propose `covered → unverified` only as data, with no filesystem registry change. Exit zero with weak-only assertions is `PASS_UNVERIFIED`. Missing/inconsistent evidence, missing artifacts, identity/hash mismatches or unverified redaction cannot yield a verified pass. An executed zero/skip/fixme/filtered case is `NOT_EXECUTED`/`UNVERIFIED`. A synthetic happy case may return `PASS_VERIFIED` **within fixture evaluation** with `live_coverage_credit: false`; an ad-hoc fixture always has no coverage credit. Only an independently observed real Playwright run could support actual coverage, outside M4.
